## 三、历史经验

### 3.1 合并策略实现

**三种模式核心逻辑**：

```php
// merge（合并，默认）— 子渠道补充父渠道配置
$result = $parentConfig;
foreach ($childConfig as $key => $value) {
    if ($value !== null) $result[$key] = $value;  // 子有则用子
}

// override（覆盖）— 完全使用子渠道配置
$result = $childConfig;

// extend（扩展）— 数组追加
$result = array_merge_recursive($parentConfig, $childConfig);
```

### 3.2 递归查询最佳实践

参考 Menu 树构建经验（最大深度 6 层），采用迭代+深度限制策略，避免递归内存问题。

### 3.3 循环引用检测

- **每次保存渠道时**执行循环检测（saving 事件中）
- **深度硬限制**：即使无循环，超过 5 层也拒绝
- 算法：visited 数组 + 深度计数

### 3.4 缓存设计策略

- **第一阶段暂不实现缓存**：渠道配置变更频率低，继承链最多 5 层性能影响有限
- **后续优化**：参考 `DictService` 的 `Cache::cacheCall + CacheTag` 模式

### 3.5 向后兼容经验

- `parent_id` 为 null 时保持原行为（不继承），保证 100% 向后兼容
- 新增 `getEffectiveConfig()` 方法，不修改现有字段使用逻辑
- 改造入口在 `ProviderManager::getForChannel()`，先解析继承再用配置

## 四、方案与任务拆分

### 4.1 实现方案概述

**架构设计**：独立服务模式，与 ChannelAffinity、CodingStatus 等服务保持一致。

```
app/Services/ChannelInheritance/
├── ChannelInheritanceResolver.php   # 核心解析服务
└── Exceptions/
    └── InheritanceResolverException.php  # 继承异常
```

**解析流程**：
```
ProviderManager::getForChannel($channel)
    │
    ├─ parent_id == null ?  → 原逻辑（向后兼容）
    │
    └─ parent_id != null
        │
        └─ ChannelInheritanceResolver::resolveConfig($channel)
            │
            ├─ 1. 构建继承链 [root, ..., parent, child]
            ├─ 2. 循环检测（已访问集合）
            ├─ 3. 深度限制（max 5）
            └─ 4. 按 inherit_mode 合并
```

**三种模式语义**：

| 模式 | 标量字段 (base_url, api_key) | 数组字段 (config, forward_headers) |
|------|---------------------------|----------------------------------|
| merge (默认) | 子空值继承父值 | array_replace_recursive（关联键覆盖） |
| override | 完全用子值（不继承） | 完全用子数组（不继承） |
| extend | 子空值继承父值 | array_merge（索引追加） |

### 4.3 风险点

1. **N+1 查询**：继承链遍历可能触发多次查询。链最多 5 级，影响可控。
2. **override 空值语义**：override 模式下子渠道 api_key 为空时不继承，可能导致 Provider 实例化失败（预期行为）。
3. **config 嵌套结构**：extend 模式对关联数组仍为键覆盖，仅对索引数组追加。

## 五、方案审阅

### 5.1 审阅结论

**采纳的修改**：
1. **移除 extend 模式**：与 merge 差异太小，简化为 merge + override 两种模式
2. **override 重新定义**：override 模式下标量字段仍继承父值（空值继承），但数组字段完全使用子值
3. **多级继承规则**：每级独立解析，从根到子逐级合并，override 仅影响当前级
4. **channel_models 纳入继承**：merge 模式下合并模型列表
5. **provider 纳入继承**：子渠道 provider 为空时继承父渠道
6. **软删除处理**：继承解析时检查父渠道 deleted_at，软删除视为不存在
7. **可继承字段白名单**：base_url, api_key, provider, config, forward_headers, channel_models

**不采纳的建议**：
- 并发循环检测：概率极低，Resolver 运行时内置检测已足够
- 请求级缓存：第一版不实现，5级查询影响可控

### 5.2 更新后的继承模式

**两种模式**：

| 模式 | 标量字段 | 数组字段 |
|------|---------|---------|
| merge (默认) | 子空值继承父值 | array_replace_recursive（深度合并） |
| override | 子空值继承父值 | 完全使用子数组 |

**关键区别**：override 仅影响数组字段（config, forward_headers, channel_models），标量字段行为与 merge 一致。

**完成时间**: 2026-07-31

**修改文件**: `app/Admin/Controllers/ChannelController.php`

**实现内容**:

1. **在 saving 回调中添加继承校验逻辑**:
   - 当 `parent_id` 被设置时，验证继承链不会形成循环
   - 使用 Channel 模型的 `hasCircularInheritance()` 方法检测循环
   - 使用 `getInheritanceDepth()` 方法检测继承深度是否超过 5 级

2. **关键代码实现**:
   ```php
   // 检测循环继承和深度限制
   $parentId = $form->parent_id;
   if ($parentId) {
       // 临时设置 parent_id 用于检测
       $channel = $form->model();
       $channel->parent_id = $parentId;
       
       // 循环检测
       if ($channel->hasCircularInheritance()) {
           return $form->response()->error('检测到循环继承，无法保存');
       }
       
       // 深度检测
       if ($channel->getInheritanceDepth() > 5) {
           return $form->response()->error('继承深度超过5级限制，无法保存');
       }
   }
   ```

3. **错误提示方式**:
   - 使用 Dcat Admin 的 `$form->response()->error()` 方法返回错误提示
   - 中文提示信息："检测到循环继承，无法保存"、"继承深度超过5级限制，无法保存"

**实现约束满足**:

### T6: ProviderManager 集成 - 已完成

**完成时间**: 2026-07-31

**修改文件**: `app/Services/Provider/ProviderManager.php`

**实现内容**:

1. **修改 `getForChannel()` 方法**:
   - 添加继承支持逻辑，使用 `$channel->hasParent()` 判断是否需要继承解析
   - 有父渠道时使用继承便捷方法获取配置
   - 无父渠道时保持原有行为（向后兼容）

2. **字段访问替换**:
   | 原字段访问 | 新继承方法 | 场景 |
   |-----------|-----------|------|
   | `$channel->provider` | `$channel->getEffectiveProvider()` | 有父渠道时 |
   | `$channel->base_url` | `$channel->getEffectiveBaseUrl()` | 有父渠道时 |
   | `$channel->api_key` | `$channel->getEffectiveApiKey()` | 有父渠道时 |
   | `$channel->getForwardHeaderNames()` | `$channel->getEffectiveForwardHeaders()` | 有父渠道时 |
   | `$channel->config` | `$channel->getResolvedConfig()['config']` | 有父渠道时 |

3. **性能优化**:
   - 只在 `$channel->hasParent()` 返回 true 时才调用继承解析方法
   - 无父渠道时保持原有的直接字段访问，避免不必要的性能损耗

**关键代码逻辑**:
```php
// 根据是否有父渠道选择配置获取方式
if ($channel->hasParent()) {
    // 有父渠道：使用继承便捷方法获取最终生效的配置
    $providerName = $channel->getEffectiveProvider() ?? $channel->provider_type ?? 'openai';
    $baseUrl = $channel->getEffectiveBaseUrl();
    $apiKey = $channel->getEffectiveApiKey();
    $forwardHeaders = $channel->getEffectiveForwardHeaders();
    $resolvedConfig = $channel->getResolvedConfig();
} else {
    // 无父渠道：向后兼容，直接使用字段值
    $providerName = $channel->provider ?? $channel->provider_type ?? 'openai';
    $baseUrl = $channel->base_url;
    $apiKey = $channel->api_key;
    $forwardHeaders = $channel->getForwardHeaderNames();
    $resolvedConfig = [];
}
```

**实现约束满足**:
- 使用 `$channel->hasParent()` 判断是否需要继承解析
- 只在有必要时才调用继承方法，避免性能损耗
- 未修改 Provider Driver 的接口和实现
- 保持中文注释
- 向后兼容：`parent_id` 为 null 时行为不变
- 保持原有错误处理逻辑

### 9.1 渠道模型（channel_models）集成缺口修复

**修复时间**: 2026-07-31

**问题描述**: `ChannelInheritanceResolver::resolveChannelModels()` 和 `Channel::getEffectiveChannelModels()` 已实现模型列表继承解析，但 `ChannelRouterService` 中两个关键方法直接查询 `channel_models` 表，绕过了继承解析，导致子渠道无法通过继承获得父渠道的模型支持。

**缺口 1: `getChannelIdsForModel()` (原第 368-374 行)**

- **问题**: 直接 `ChannelModel::where('model_name', $model)` 查询，子渠道没有自己的 channel_models 记录时不会被选中
- **修复**: 在直接查询基础上，遍历子渠道（排除已有该模型的渠道），调用 `getEffectiveChannelModels()` 检查继承后的模型列表
- **性能说明**: 子渠道数量有限，暂不做缓存优化

**缺口 2: `resolveModel()` (原第 531-583 行)**

- **问题**: 直接 `ChannelModel::where('channel_id', $channel->id)` 查询，子渠道无法获取继承来的模型映射
- **修复**: 在直接查询未命中后，若渠道有父渠道（`$channel->hasParent()`），从 `getEffectiveChannelModels()` 返回的继承模型列表中查找映射
- **查找顺序**: ① 渠道自身 channel_models（别名匹配）→ ② 继承模型列表（有父渠道时）→ ③ 渠道自身 channel_models（原模型名匹配，兜底）→ ④ 返回原模型名

**修改文件**: `app/Services/Router/ChannelRouterService.php`

**向后兼容**: 无父渠道时行为完全不变（`hasParent()` 返回 false 则跳过继承查找）
