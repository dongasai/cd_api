## 严重问题（需修复后才能上线）

### S1. ProviderManager 重复遍历继承链，造成 4 倍性能浪费

**文件**: `app/Services/Provider/ProviderManager.php:105-141`

```php
// 当前代码：有父渠道时
$providerName = $channel->getEffectiveProvider();   // 遍历1次继承链
$baseUrl = $channel->getEffectiveBaseUrl();          // 遍历2次
$apiKey = $channel->getEffectiveApiKey();            // 遍历3次
$forwardHeaders = $channel->getEffectiveForwardHeaders(); // 遍历4次
$resolvedConfig = $channel->getResolvedConfig();     // 遍历5次
```

每次 `getEffective*` 调用都触发一次完整的继承链构建（最多 5 次数据库查询）。

**修复方案**: 直接复用 `$resolvedConfig` 中的值：

```php
if ($channel->hasParent()) {
    $resolvedConfig = $channel->getResolvedConfig();
    $providerName = $resolvedConfig['provider'] ?? $channel->provider_type ?? 'openai';
    $baseUrl = $resolvedConfig['base_url'];
    $apiKey = $resolvedConfig['api_key'];
    $forwardHeaders = $resolvedConfig['forward_headers'];
}
```

### S2. `forward_headers` 为索引数组时 MERGE 行为不符合预期

**文件**: `ChannelInheritanceResolver.php:174-184`

`forward_headers` 在数据库和表单中都是**索引数组**（`['X-Header-A', 'X-Header-B']`），但代码使用 `array_replace_recursive` 合并：

```php
// 父: ['X-Parent-Header']  子: ['X-Child-Header']
// array_replace_recursive 结果: ['X-Child-Header']  ← 子覆盖父，不是追加！
```

对于索引数组，`array_replace_recursive` 会按键（0,1,2...）覆盖，而非追加。实际行为等同于 OVERRIDE，与 MERGE 语义矛盾。

**修复方案**: 对 `forward_headers` 使用 `array_unique(array_merge(...))` 合并：

```php
if ($field === 'forward_headers') {
    $result[$field] = array_values(array_unique(array_merge(
        $parentValue ?? [],
        $childValue ?? []
    )));
} else {
    $result[$field] = array_replace_recursive($parentValue, $childValue);
}
```

**同时**: 单元测试 `test_single_level_merge_inheritance_merges_configs` 第 104 行的断言 `['X-Parent-Header', 'X-Child-Header']` 在当前实现下**不会通过**（实际结果是 `['X-Child-Header']`）。

### S3. ProviderManager 中引用不存在的字段 `provider_type`

**文件**: `ProviderManager.php:107,114`

```php
$providerName = $channel->getEffectiveProvider() ?? $channel->provider_type ?? 'openai';
```

`Channel` 模型没有 `provider_type` 属性（数据库和模型中均不存在）。Eloquent 动态属性访问不存在的字段返回 null，不会报错，但这是误导性的死代码。

**修复**: 移除 `provider_type` 回退，直接使用 `provider`：

```php
$providerName = $resolvedConfig['provider'] ?? 'openai';
```

## 重要问题（建议本迭代修复）

### M1. Channel 模型未使用 SoftDeletes trait，但 Resolver 手动检查 `deleted_at`

**文件**: `ChannelInheritanceResolver.php:115-117`

Channel 模型**没有** `use SoftDeletes`，因此 `parent()` BelongsTo 关系**不会**自动过滤软删除记录。Resolver 手动检查 `$parent->deleted_at !== null` 是正确的补偿逻辑。

但这存在隐患：
- 如果将来给 Channel 添加 SoftDeletes trait，`parent()` 关系会自动过滤，Resolver 的手动检查将变成多余（但不影响正确性）
- 当前 `parentSoftDeleted` 异常路径**可以正常触发**（因为关系会返回有 `deleted_at` 的记录）

**建议**: 在 Resolver 中添加注释说明为何手动检查 deleted_at，与模型缺少 SoftDeletes trait 保持一致。

---

### M2. 详情页继承预览重复查询

**文件**: `ChannelController.php:225-368`

详情页中多次调用继承解析方法，每次都重新构建继承链：

- `getInheritanceChain()` — 第 226 行
- `getInheritanceDepth()` — 第 250 行
- `getResolvedConfig()` — 第 308 行（在 effective_config 闭包中）
- `getEffectiveForwardHeaders()` — 第 320 行
- `getEffectiveChannelModels()` — 第 345 行
- 继承来源查找中再次调用 `getInheritanceChain()` — 第 290 行

**建议**: 在 `detail()` 方法开头预计算一次，通过 `use` 传递到闭包中。

### M3. InheritMode 枚举 label() 硬编码中文，与多语言体系不一致

**文件**: `app/Enums/InheritMode.php:44-49`

```php
public function label(): string
{
    return match ($this) {
        self::MERGE => '合并',
        self::OVERRIDE => '覆盖',
    };
}
```

项目有中英文语言包（`lang/zh_CN/admin-channel.php`, `lang/en/admin-channel.php`），但 `label()` 直接硬编码中文。英文环境下继承链显示仍为中文标签。

**修复**: 使用 `admin_trans()` 或语言包键值：

```php
public function label(): string
{
    return match ($this) {
        self::MERGE => admin_trans('admin-channel.options.inherit_mode.merge'),
        self::OVERRIDE => admin_trans('admin-channel.options.inherit_mode.override'),
    };
}
```

### M4. 数据库迁移仍包含 `extend` 枚举值，但代码已移除

**文件**: `database/migrations/2026_03_07_083340_create_channels_table.php:22`

```php
$table->enum('inherit_mode', ['merge', 'override', 'extend'])->default('merge');
```

代码中 `InheritMode` 枚举只有 MERGE 和 OVERRIDE，但数据库枚举仍有 `extend`。如果有旧数据的 `inherit_mode` 为 `'extend'`，`InheritMode::tryFrom('extend')` 返回 null，fallback 为 MERGE（正确行为），但应记录在文档中。

**建议**: 创建新迁移移除 `extend` 枚举值，或将现有 `extend` 值更新为 `merge`。

---

### M5. Channel 模型便捷方法每次调用 `app()` 解析服务

**文件**: `app/Models/Channel.php:523-694`

每个继承便捷方法都调用 `app(ChannelInheritanceResolver::class)`。Laravel 容器会缓存单例（如果是注册为单例的），但如果 Resolver 没有被注册为单例，每次都会创建新实例。

**建议**: 在 `bootstrap/providers.php` 中将 `ChannelInheritanceResolver` 注册为单例，或在 Channel 模型中使用属性缓存已解析结果。

## 改进建议

### I1. `resolveConfigs` 批量方法未做查询优化

**文件**: `ChannelInheritanceResolver.php:405-413`

```php
public function resolveConfigs(array $channels): array
{
    foreach ($channels as $channel) {
        $result[$channel->id] = $this->resolveConfig($channel);
    }
}
```

批量解析时，每个渠道独立构建继承链，父渠道的 `channelModels` 会被重复查询。

**建议**: 预加载所有渠道的 parent 关系和 channelModels，或使用 CTE 递归查询构建继承链。

---

### I2. 异常类 `invalidConfig` 工厂方法未使用

`InheritanceResolverException::invalidConfig()` 已定义但从未被调用。`TYPE_INVALID_CONFIG` 常量也只在 `isRecoverable()` 中引用。

**建议**: 如果暂不使用，标记为 `@todo` 或移除。

---

### I3. 测试 `test_parent_soft_deleted` 依赖 Channel 不使用 SoftDeletes

如果将来给 Channel 模型添加 `SoftDeletes` trait，`BelongsTo` 关系将自动排除软删除记录，`$current->parent` 返回 null，触发 `parentNotFound` 而非 `parentSoftDeleted`。测试会失败。

**建议**: 测试中添加注释说明前置条件，或在 `parent()` 关系上添加 `->withTrashed()` 确保行为一致。

---

### I4. `hasCircularInheritance()` 无深度限制

与 `getInheritanceChain()` 不同，`hasCircularInheritance()` 没有 MAX_DEPTH 保护。在极端异常场景下（深度极大的链），可能长时间遍历。

**建议**: 添加安全深度上限（如 100）。

---

### I5. 表单保存回调中深度限制硬编码为 5

**文件**: `ChannelController.php:591`

```php
if ($channel->getInheritanceDepth() > 5) {
```

与 `ChannelInheritanceResolver::MAX_DEPTH` 常量不同步。

**修复**: 使用常量引用：

```php
if ($channel->getInheritanceDepth() > ChannelInheritanceResolver::MAX_DEPTH) {
```

## 审查总结

| 等级 | 数量 | 关键问题 |
|------|------|---------|
| 严重 | 3 | 性能浪费(4x查询)、forward_headers 合并逻辑错误、死代码字段 |
| 重要 | 5 | SoftDeletes 不一致、详情页重复查询、硬编码中文、数据库枚举残留、服务解析 |
