# 任务规划：API Key 分组/标签访问控制

## 任务目标

在 `api_keys` 表新增 `allowed_groups`、`not_allowed_groups`、`allowed_tags`、`not_allowed_tags` 四个 JSON 字段，实现 Key 级别的分组/标签访问控制。

## 确认理解

- **数据结构**：方案 A - 新增独立字段（与现有 allowed_channels/not_allowed_channels 风格一致）
- **分组用 slug 存储**，标签用 name 存储（字符串数组）
- **支持黑白名单**：分组和标签都支持白名单和黑名单
- **过滤顺序**：黑名单（渠道）→ 白名单（渠道）→ 分组黑名单 → 分组白名单 → 标签黑名单 → 标签白名单
- **Admin 界面**：需要更新 ApiKeyController 表单，添加分组/标签多选选择器
- **配合策略**：渠道 ID 过滤先执行，分组/标签在其后进一步过滤，层层收紧（交集）

## 经验教训

1. **JSON 字段类型安全**：getter 方法做 `array_map('strval', ...)` 确保类型安全
2. **Dcat Admin multipleSelect Bug**：saving 回调做 `array_values()` 确保索引连续
3. **查询性能**：使用 Collection 过滤 + eager load 避免 N+1
4. **无 Redis 依赖**：不要在过滤逻辑中使用缓存锁或 Redis 驱动
5. **分组用 slug，标签用 name**：字符串存储更稳定
6. **边缘案例**：分组/标签删除后静默忽略

## 过滤逻辑设计

```
黑名单（渠道 ID）→ 白名单（渠道 ID）→ 黑名单（分组 slug）→ 白名单（分组 slug）→ 黑名单（标签 name）→ 白名单（标签 name）
```

- 分组黑名单：渠道属于黑名单分组 → 排除
- 分组白名单：渠道必须属于白名单分组之一 → 保留
- 标签黑名单：渠道拥有黑名单标签 → 排除
- 标签白名单：渠道必须拥有白名单标签之一 → 保留
- 无配置则不限制

## 风险与注意事项

1. **N+1 查询**：必须在查询时 eager load groups/tags 关系
2. **缓存一致性**：ModelService 缓存 key 需包含分组/标签配置 hash
3. **Dcat Admin multipleSelectTable**：分组用 slug 存储值，标签用 name 存储值
4. **ChannelAffinityService 兼容**：需改为 isChannelAllowedWithGroupsAndTags
5. **空值安全**：四个新字段默认 null，getter 必须处理 null 返回空数组
