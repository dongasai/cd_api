# 系统日志表分析

## 日志体系概览

系统采用 **1+3** 日志架构：1 个审计日志（元数据中枢）+ 3 个明细日志（请求/响应/渠道），通过 `request_id` 和 `audit_log_id` 串联完整请求链路。

```
客户端请求 → AuditLog(元数据) + RequestLog(请求内容)
                ↓ 渠道选择
           ChannelRequestLog(渠道交互)
                ↓ 响应处理
           ResponseLog(响应内容)
```

---

## 核心日志表（请求链路）

### 1. AuditLog 审计日志 — 请求元数据中枢

**作用**：记录每次 API 请求的元数据摘要，是日志体系的中心节点，关联其他三张日志表。

**核心字段**：

| 分类 | 字段 | 说明 |
|------|------|------|
| 身份 | `user_id`, `username`, `api_key_id`, `api_key_name` | 请求者身份 |
| 渠道 | `channel_id`, `channel_name` | 最终使用的渠道 |
| 标识 | `request_id`(唯一), `run_unid`(运行标识) | 请求追踪 |
| 模型 | `model`(请求模型), `actual_model`(实际模型) | 模型映射结果 |
| 协议 | `source_protocol`, `target_protocol` | 协议转换方向 |
| Token | `prompt_tokens`, `completion_tokens`, `total_tokens`, `cache_read/write_tokens` | 用量统计 |
| 计费 | `cost`(美元), `quota`(配额), `billing_source` | 成本核算 |
| 性能 | `latency_ms`, `first_token_ms`, `is_stream` | 延迟指标 |
| 状态 | `status_code`, `finish_reason`, `error_type`, `error_message` | 请求结果 |
| 路由 | `group_name`, `channel_affinity`(JSON) | 渠道路由信息 |
| 扩展 | `apply_data`(JSON), `metadata`(JSON) | 模型流转过程、额外数据 |

**模型关系**：
- `requestLog()` → HasOne RequestLog
- `responseLog()` → HasOne ResponseLog
- `channelRequestLogs()` → HasMany ChannelRequestLog

**关键索引**：`request_id`, `api_key_id+created_at`, `channel_id+created_at`, `model+created_at`, `status_code+created_at`

---

### 2. RequestLog 请求日志 — 客户端请求完整内容

**作用**：记录客户端发送到本系统的完整请求内容，用于请求重放和问题排查。

**核心字段**：

| 分类 | 字段 | 说明 |
|------|------|------|
| 关联 | `audit_log_id`, `request_id`, `run_unid` | 关联审计日志 |
| HTTP | `method`, `path`, `query_string`, `headers`(JSON) | 请求元信息 |
| 内容 | `body_text`(longText), `body_binary`(blob), `content_type`, `content_length` | 请求体 |
| 模型 | `model`, `upstream_model`, `model_params`(JSON) | 模型参数 |
| 消息 | `messages`(JSON), `prompt`(text) | 聊天/补全内容 |
| 脱敏 | `sensitive_fields`(JSON), `has_sensitive` | 敏感信息标记 |

**与 AuditLog 的区别**：AuditLog 记录摘要元数据，RequestLog 记录完整请求体（含 messages、prompt 等大字段）。

---

### 3. ResponseLog 响应日志 — 上游响应完整内容

**作用**：记录上游返回的完整响应内容，包括生成的文本、Token 用量、错误详情。

**核心字段**：

| 分类 | 字段 | 说明 |
|------|------|------|
| 关联 | `audit_log_id`, `request_id`, `request_log_id` | 关联审计+请求日志 |
| HTTP | `status_code`, `status_message`, `headers`(JSON) | 响应状态 |
| 内容 | `body_text`(longText), `body_binary`(blob), `content_type`, `content_length` | 响应体 |
| 类型 | `response_type`(chat/completion/embedding/error), `finish_reason` | 响应分类 |
| 生成 | `generated_text`(longText), `generated_chunks`(JSON) | AI 生成内容 |
| 用量 | `usage`(JSON) | Token 使用详情 |
| 错误 | `error_type`, `error_code`, `error_message`, `error_details`(JSON) | 错误信息 |
| 上游 | `upstream_provider`, `upstream_model`, `upstream_latency_ms` | 上游信息 |

**`generated_text` vs `body_text`**：`body_text` 是原始响应体，`generated_text` 是提取的纯文本内容（便于查看和搜索）。

---

### 4. ChannelRequestLog 渠道请求日志 — 与上游的完整交互

**作用**：记录本系统与上游渠道的完整交互过程，包括发送的请求和收到的响应。一次请求可能产生多条记录（重试/故障转移）。

**核心字段**：

| 分类 | 字段 | 说明 |
|------|------|------|
| 关联 | `audit_log_id`, `request_log_id`, `request_id` | 关联其他日志 |
| 渠道 | `channel_id`, `channel_name`, `provider` | 渠道信息 |
| 请求 | `method`, `path`, `base_url`, `full_url` | 请求地址 |
| 请求数据 | `request_headers`(JSON), `request_body`(longText), `request_size` | 发给上游的内容 |
| 响应数据 | `response_status`, `response_headers`(JSON), `response_body`(longText), `response_body_chunks`(JSON), `response_size` | 上游返回的内容 |
| 性能 | `latency_ms`, `ttfb_ms`(首字节时间) | 延迟指标 |
| 结果 | `is_success`, `error_type`, `error_message` | 交互结果 |
| 用量 | `usage`(JSON) | Token 使用 |

**与 RequestLog/ResponseLog 的区别**：RequestLog 记录客户端→本系统的请求，ChannelRequestLog 记录本系统→上游的请求（含协议转换后的内容）。

---

## 辅助日志表

### 5. ChannelForwardingLog 渠道转发日志

**作用**：记录请求在渠道间的转发/重试路径，追踪故障转移链路。

**关键字段**：`hop_index`(跳数: 0=首次, 1=第一次重试), `is_final`, `fallback_reason`, `skip_reason`

### 6. ChannelErrorHandlingLog 渠道错误处理日志

**作用**：记录渠道错误触发的自动处理动作（暂停渠道、降级等）。

**关键字段**：`action_taken`, `pause_duration_minutes`, `triggered_by`(auto/manual)

### 7. OperationLog 操作日志

**作用**：记录后台管理操作（增删改），支持审计追溯。

**关键字段**：`type`(操作类型), `target`(操作对象), `before_data/after_data`(变更前后数据)

### 8. ModelTestLog 模型测试日志

**作用**：记录渠道测试和系统测试的结果。

**关键字段**：`test_type`(channel_direct/system_api), `assistant_response`, `response_time_ms`

## 日志创建流程

```
ProxyServer::proxy()
  │
  ├─ 1. 生成 request_id (UUID)
  ├─ 2. AuditLogger::createInitial()     → 创建 AuditLog（初始状态）
  ├─ 3. RequestLogger::create()           → 创建 RequestLog（完整请求）
  ├─ 4. RequestLogger::updateModel()      → 更新模型参数
  ├─ 5. ChannelRouterService::select()    → 选择渠道
  ├─ 6. AuditLogger::update()             → 更新 AuditLog（渠道/模型/协议）
  ├─ 7. 创建 ChannelRequestLog            → 记录渠道交互
  ├─ 8. StreamHandler / NonStreamHandler  → 处理响应
  │     └─ ResponseLogger::create()       → 创建 ResponseLog
  └─ 9. AuditLogger::update()             → 更新 AuditLog（最终状态/Token/延迟）
```

## 日志关联关系

```
AuditLog (中心)
  ├── HasOne  → RequestLog  (audit_log_id)
  ├── HasOne  → ResponseLog (audit_log_id)
  └── HasMany → ChannelRequestLog (audit_log_id)

ResponseLog
  └── BelongsTo → RequestLog (request_log_id)

ChannelRequestLog
  └── BelongsTo → RequestLog (request_log_id)

通用关联键: request_id (贯穿所有日志表)
```

## 日志存储配置

`log_storage_config` 表控制日志存储策略：
- `store_request_body` / `store_response_body` — 是否存储请求/响应体
- `store_headers` / `store_messages` / `store_generated_text` — 细粒度控制
- `mask_sensitive` — 敏感信息脱敏
- `sample_rate` — 采样率 (0-1)
- `retention_days` — 保留天数
- 支持 global 和 api_key 两种作用域
